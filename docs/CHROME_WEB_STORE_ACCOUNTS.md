# Chrome Web Store: аккаунты и публикация нескольких расширений

Гид для случая «несколько своих расширений, возможно под разными брендами».
Все факты ниже — из официальной документации Chrome Web Store; ссылки в конце.

## TL;DR

- Один **Google-аккаунт** = один **developer**. Регистрация $5 **один раз**, а не
  за каждое расширение.
- Внутри developer можно завести **второй publisher** (итого два). Это
  официально разрешено и даёт **два отдельных бренда** с раздельными листингами.
- **Лимит расширений — 2 на нового publisher.** Это ключевое ограничение, и оно
  не обходится количеством аккаунтов.
- Обход лимита через связанные аккаунты — прямое нарушение с формулировкой
  «immediate termination of your developer account, and possibly related
  developer accounts». Один забаненный аккаунт тянет за собой остальные.
- **Email аккаунта изменить нельзя.** Только создавать новый и переносить items.

## Термины, чтобы не путаться

| Сущность | Что это | Сколько можно |
|---|---|---|
| Google-аккаунт | Вход в дашборд, одна почта | По числу ваших почт |
| Developer | Профиль разработчика, привязан к Google-аккаунту | 1 на Google-аккаунт |
| Publisher | Владелец items, показывает имя под заголовком расширения | **1 + 1 дополнительный** на developer |
| Item | Одно расширение в сторе | **2 на publisher** у новичка |

Расширения принадлежат **publisher'у**, а не developer'у. Поэтому «два аккаунта»
на практике означает «два publisher'а», и оба могут жить под одним логином.

## Путь A: один аккаунт, два издателя (рекомендуется)

Официально: «A publisher is created when you first register as a developer, and
you can create one additional publisher if needed».

1. **Завести отдельную почту** под публикации. Например
   `publisher@ваш-домен` или отдельный Gmail. Документация рекомендует именно
   так: почту потом не сменить, а на неё приходят уведомления о снятии и
   отклонении.
2. **Включить 2FA** на этом Google-аккаунте. Без 2-Step Verification публикация
   и обновления заблокированы — это требование политики, не рекомендация.
3. **Зарегистрироваться**: открыть
   [developer dashboard](https://chrome.google.com/webstore/devconsole), принять
   Developer Agreement, оплатить **$5** (картой; разовый платёж).
4. **Заполнить профиль**: publisher name (виден под каждым расширением),
   контактный email + подтвердить его по ссылке из письма. Физический адрес —
   только если планируете брать деньги с пользователей.
5. **Создать второго издателя**: страница Profile → «Create a new publisher».
   Дать ему имя второго бренда. Переключение — выпадающий список в правом
   верхнем углу дашборда.
6. **Приглашать соавторов при необходимости**: Settings внутри publisher →
   «Invite member» → роль. Роли: Viewer / Item Manager / Editor / Admin.
   `Item Manager` достаточно для загрузки и обновления пакетов.

**Что это даёт:** два независимых бренда (например, CineSync и второй продукт),
раздельные листинги и разные publisher name под заголовками. Аккаунт один,
$5 одни, 2FA одни.

**Чего это не даёт:** суммарный лимит остаётся 2 + 2. Если расширений больше
четырёх, нужен запрос на увеличение лимита (см. ниже), а не второй аккаунт.

## Путь B: два независимых Google-аккаунта

Иногда нужен для полной изоляции (разные юрлица, разные команды, разные
страны). Стоит понимать цену:

- **$5 дважды** — регистрация платится за каждый developer-аккаунт.
- **2FA, профиль, подтверждение почты** — заводится в каждом.
- **Аккаунты считаются «связанными»** (related), если Google может их связать:
  общий платёжный инструмент, общий адрес, общий домен, кросс-продвижение,
  одинаковые items. Политика Spam and Abuse оперирует именно связкой
  «developer, related developer accounts, or their affiliates».
- **Риск общий.** Enforcement Circumvention: попытка обойти лимиты →
  немедленное закрытие аккаунта **и связанных с ним**. Поэтому два аккаунта —
  это не страховка от бана, а наоборот: увеличивает площадь поражения.

**Вывод:** второй аккаунт оправдан только как настоящая организационная
граница, а не как способ получить больше расширений. Для «своих расширений под
разными брендами» Путь A делает то же самое дешевле и без риска.

## Лимит на количество расширений

Дословно из документации Publish:

> When you first create your publisher in the Chrome Web Store, you will be
> limited to a maximum of two published extensions. […] If you have reached the
> limit, you will be given the option to request an increase. In most cases, you
> will receive an immediate decision […] This limit does not apply to themes.

Практика:

- **Лимит виден в дашборде** и запрашивается кнопкой там же; часто решение
  приходит мгновенно.
- **Отказ** обычно мотивируют двумя причинами: у уже опубликованных расширений
  недостаточная вовлечённость (sustained engagement) либо у publisher'а не
  хватает «срока и активности» (tenure and activity requirements).
- **Темы (themes) не считаются** — если делаете тему, слот не тратится.
- **Лимит per-publisher**, поэтому два publisher'а дают 4 слота при $5.

**Практический вывод:** чтобы держать путь к увеличению лимита открытым,
первый релиз стоит делать качественно, а не «наполнителем» — метрики
вовлечённости на опубликованном расширении влияют на следующее решение.

## Чек-лист публикации

### Один раз

- [ ] Отдельная почта под публикации, 2FA включена
- [ ] Регистрация developer ($5), профиль заполнен
- [ ] Контактный email подтверждён
- [ ] Второй publisher создан (если нужен второй бренд)

### Для каждого расширения

- [ ] Пакет: валидный ZIP, `manifest.json` в корне, **без** `node_modules`,
      `src`, конфигов сборки
- [ ] Иконки: 16/32/48/128 в манифесте
- [ ] Скриншоты: минимум один **1280×800** (до 5), затем промо-плитки
- [ ] Store listing: описание, категория, язык
- [ ] Privacy: single purpose, обоснование **каждого** разрешения, data usage
- [ ] Distribution: страны, кто видит листинг
- [ ] Support / Homepage URL (по желанию, но полезно)
- [ ] Test instructions — если для проверки нужен вход или ключи

### Требования, на которых чаще всего спотыкаются

- **Privacy policy обязателен** и должен **совпадать** с полями Privacy в
  дашборде и с реальным поведением кода. Расхождение → снятие с публикации.
- **Обоснование каждого разрешения** сверяется с манифестом. Лишнее разрешение
  без использования — частая причина отказа. У CineSync это уже вычищено
  (`activeTab` убран).
- **Listing requirements**: пустое описание, отсутствие иконки или скриншота →
  отклонение. Keyword spam (перечисление брендов без ценности, повтор слова
  более 5 раз) запрещён.
- **Impersonation**: нельзя выглядеть как одобренное другой компанией. Поэтому
  бренд чужого сервиса не стоит ставить в название продукта — только в
  описание как «работает с …».
- **Код должен быть читаемым** после сборки; обфускация ради сокрытия логики
  нарушает Code Readability Requirements. Минификация бандлера допустима.
- **MV3 обязателен.** MV2 удалён из стора 31 августа 2026.

## Как это применить к текущему проекту

Расширение переименовано в **CineSync** специально под путь A:

- Имя больше не содержит чужого бренда (было «Kinopoisk …») — снимает риск по
  Impersonation, и Кинопоиск остался только в описании как поддерживаемый сервис.
- Имя описывает функцию (синхронизация между сервисами), а не одно направление
  «KP → TMDB», что честнее для мультиматрицы и лучше для поиска.
- Отдельная почта под публикации + второй publisher под второй бренд — это
  ровно тот сценарий, под который писалась документация про additional
  publisher.

## Проверить перед подачей

- [ ] `npm run package` → `cinesync-3.2.0.zip`; убедиться, что внутри ровно
      то, что грузит манифест
- [ ] Версия — **строго выше** предыдущей опубликованной (стор не примет ту же)
- [ ] Скриншоты 1280×800 сделаны с реального попапа
- [ ] Тексты Privacy из `docs/PRIVACY.md` перенесены в дашборд без противоречий
- [ ] Описание не перечисляет бренды списком и не повторяет ключевое слово >5 раз
