# Chrome Web Store: аккаунты и публикация нескольких расширений

Гид для случая «несколько своих расширений, возможно под разными брендами».
Все факты ниже — из официальной документации Chrome Web Store; ссылки в конце.

## TL;DR — как публиковать всё с одного аккаунта

**Да, это делается с одного аккаунта.** Второй аккаунт не нужен и не помогает.

- Один **Google-аккаунт** = один developer. Регистрация **$5 один раз**, не за
  каждое расширение.
- **Лимит по умолчанию — 2 расширения на publisher.** Это единственная реальная
  преграда, и снимается она **запросом на увеличение прямо в дашборде**, а не
  вторым аккаунтом.
- Запрос подаётся из дашборда, когда упрётесь в лимит. Часто решение
  **мгновенное**; иногда отправляют в support-кейс, это несколько дней.
- Внутри аккаунта можно завести **второй publisher** — это даёт второй бренд и
  ещё 2 слота, если нужно разделить проекты.
- Обход лимита через связанные аккаунты — нарушение с формулировкой
  «immediate termination of your developer account, **and possibly related
  developer accounts**». Один аккаунт тут безопаснее двух.
- **Email аккаунта изменить нельзя.** Выбирайте почту сразу правильную.

### Порядок действий

1. Завести выделенную почту под публикации.
2. Включить 2FA на этом Google-аккаунте.
3. [developer dashboard](https://chrome.google.com/webstore/devconsole) → принять
   Developer Agreement → оплатить $5.
4. Заполнить Account: publisher name, контактный email + подтвердить.
5. Публиковать расширения (лимит 2).
6. Упереться в лимит → **запросить увеличение в дашборде** → публиковать дальше.
7. Второй publisher — только если нужен отдельный бренд.

**Two-Step Verification** — обязательна до первой публикации и до любого
обновления. Без неё дашборд не даст отправить item на ревью.

**Поддержка — только по email.** После открытия кейса вся переписка идёт
письмом на адрес publisher'а, поэтому почта должна быть рабочей и не улетать
в спам.

## Термины, чтобы не путаться

| Сущность | Что это | Сколько можно |
|---|---|---|
| Google-аккаунт | Вход в дашборд, одна почта | По числу ваших почт |
| Developer | Профиль разработчика, привязан к Google-аккаунту | 1 на Google-аккаунт |
| Publisher | Владелец items, показывает имя под заголовком расширения | **1 + 1 дополнительный** на developer |
| Item | Одно расширение в сторе | **2 на publisher** у новичка |

Расширения принадлежат **publisher'у**, а не developer'у. Поэтому «два аккаунта»
на практике означает «два publisher'а», и оба могут жить под одним логином.

## Основной путь: один аккаунт для всех расширений

Это рекомендуемый и достаточный вариант. Всё, что вам нужно — один раз
зарегистрироваться и при упоре в лимит запросить увеличение.

### Один раз

1. **Выделенная почта под публикации.** Не личный ящик: этот адрес получает
   уведомления об отклонениях и снятиях, и **сменить его потом нельзя** —
   только создавать новый аккаунт и переносить items через
   [One Stop Support](https://support.google.com/chrome_webstore/contact/one_stop_support).
   Документация сама советует отдельный ящик именно под Web Store.
2. **2FA включить сразу** —
   [ссылка](https://myaccount.google.com/security/signinoptions/two-step-verification/enroll-welcome).
   Без неё нельзя ни опубликовать, ни обновить.
3. **Зарегистрироваться**: открыть
   [дашборд](https://chrome.google.com/webstore/devconsole), принять Developer
   Agreement, оплатить **$5**. Платёж разовый на весь аккаунт.
4. **Заполнить Account → Profile**: publisher name (виден под каждым
   расширением), контактный email → подтвердить по ссылке из письма.
   Физический адрес — только если планируете брать деньги с пользователей.

### Дальше — просто публикуйте

5. **Публикуйте расширения** обычным порядком, пока не упрётесь в лимит 2.
6. **Упёрлись** → в дашборде появится запрос на увеличение → отправляйте.
7. **Получили слоты** → публикуйте остальные. Повторяйте по мере роста.

### Опционально: второй publisher под второй бренд

Официально разрешено: «A publisher is created when you first register as a
developer, and you can create one additional publisher if needed».

- Profile → **Create a new publisher** → задать имя второго бренда.
- Даёт отдельное имя под заголовком и отдельный листинг, **плюс 2 слота**.
- Переключение между publisher'ами — выпадающий список в правом верхнем углу
  дашборда.
- Соавторов добавлять через Settings внутри publisher → **Invite member**.
  Роли: Viewer / Item Manager / Editor / Admin. Для загрузки пакетов хватает
  `Item Manager`, для управления ролями нужен только `Admin`.

Это полезно для разделения проектов по бренду, но **не обязательно**: при
одном бренде достаточно запрашивать увеличение лимита на основном publisher.

## Второй аккаунт: когда он вообще оправдан

Он нужен только для настоящей организационной границы — разные юрлица, разные
команды, разные страны. Как способ получить больше расширений он не работает.
Цена, если всё-таки нужен:

- **$5 дважды** — регистрация платится за каждый developer-аккаунт.
- **2FA, профиль, подтверждение почты** — заводится в каждом.
- **Аккаунты считаются «связанными»** (related), если Google может их связать:
  общий платёжный инструмент, общий адрес, общий домен, кросс-продвижение,
  одинаковые items. Политика Spam and Abuse оперирует именно связкой
  «developer, related developer accounts, or their affiliates».
- **Риск общий.** Enforcement Circumvention: попытка обойти лимиты →
  немедленное закрытие аккаунта **и связанных с ним**. Поэтому два аккаунта —
  это не страховка от бана, а наоборот: увеличивает площадь поражения.

**Вывод:** для «все свои расширения» второй аккаунт не нужен. Один аккаунт +
запрос увеличения лимита закрывает задачу дешевле, и — главное — без общего
риска на связанные аккаунты.

## Лимит на количество расширений

Дословно из документации Publish:

> When you first create your publisher in the Chrome Web Store, you will be
> limited to a maximum of two published extensions. […] If you have reached the
> limit, you will be given the option to request an increase. In most cases, you
> will receive an immediate decision […] This limit does not apply to themes.

### Где именно запрашивать

Отдельной «страницы лимитов» не существует. Кнопка появляется **в дашборде в
момент, когда вы упрётесь в лимит**:

1. [chrome.google.com/webstore/devconsole](https://chrome.google.com/webstore/devconsole)
   — сам дашборд.
2. Дойдите до лимита (загрузите 2 расширения) — в интерфейсе появится текущий
   счётчик и кнопка запроса увеличения.
3. Если автоматического одобрения нет, откроется форма support-кейса.

### Что влияет на одобрение

Практика (ответ Diamond Product Expert в официальном сообществе, сентябрь 2026)
совпадает с документацией — решение зависит от двух вещей:

1. **Tenure and activity** — как давно существует publisher и насколько он
   активен. Свежий аккаунт с нулевой историей получает отказ чаще.
2. **Sustained user engagement** на уже опубликованных расширениях — живые
   установки, а не «залил и забыл».

Отсюда практический вывод: **первые два расширения стоит делать реально
полезными и не удалять их ради освобождения слота**. Удаление опубликованного
расширения не улучшит метрики. Хорошая история на двух items — это и есть
аргумент для увеличения лимита.

Темы (themes) **не считаются** в лимит.

### Если отказали

- Отказ не блокирует аккаунт: опубликованные расширения продолжают работать.
- Наработать историю на текущих двух и подать повторно позже.
- Обходной путь через новый аккаунт — нарушение: см. раздел про второй аккаунт выше.

## Чек-лист публикации

### Один раз

- [ ] Отдельная почта под публикации, 2FA включена
- [ ] Регистрация developer ($5), профиль заполнен
- [ ] Контактный email подтверждён
- [ ] Второй publisher создан (если нужен второй бренд)

### Для каждого расширения

- [ ] Пакет: валидный ZIP, `manifest.json` в корне, **без** `node_modules`,
      `src`, конфигов сборки
- [ ] Иконки: 16/32/48/128 в манифесте
- [ ] Скриншоты: минимум один **1280×800** (до 5), затем промо-плитки
- [ ] Store listing: описание, категория, язык
- [ ] Privacy: single purpose, обоснование **каждого** разрешения, data usage
- [ ] Distribution: страны, кто видит листинг
- [ ] Support / Homepage URL (по желанию, но полезно)
- [ ] Test instructions — если для проверки нужен вход или ключи

### Требования, на которых чаще всего спотыкаются

- **Privacy policy обязателен** и должен **совпадать** с полями Privacy в
  дашборде и с реальным поведением кода. Расхождение → снятие с публикации.
- **Обоснование каждого разрешения** сверяется с манифестом. Лишнее разрешение
  без использования — частая причина отказа. У CineSync это уже вычищено
  (`activeTab` убран).
- **Listing requirements**: пустое описание, отсутствие иконки или скриншота →
  отклонение. Keyword spam (перечисление брендов без ценности, повтор слова
  более 5 раз) запрещён.
- **Impersonation**: нельзя выглядеть как одобренное другой компанией. Поэтому
  бренд чужого сервиса не стоит ставить в название продукта — только в
  описание как «работает с …».
- **Код должен быть читаемым** после сборки; обфускация ради сокрытия логики
  нарушает Code Readability Requirements. Минификация бандлера допустима.
- **MV3 обязателен.** MV2 удалён из стора 31 августа 2026.

## Как это применить к текущему проекту

Расширение переименовано в **CineSync** под одноаккаунтную схему:

- Имя больше не содержит чужого бренда (было «Kinopoisk …») — снимает риск по
  Impersonation, и Кинопоиск остался только в описании как поддерживаемый сервис.
- Имя описывает функцию (синхронизация между сервисами), а не одно направление
  «KP → TMDB», что честнее для мультиматрицы и лучше для поиска.
- Один аккаунт покрывает все ваши расширения: два слота сразу, остальные —
  через запрос увеличения лимита. Второй publisher нужен, только если захотите
  визуально разделить бренды.

## Проверить перед подачей

- [ ] `npm run package` → `cinesync-3.2.0.zip`; убедиться, что внутри ровно
      то, что грузит манифест
- [ ] Версия — **строго выше** предыдущей опубликованной (стор не примет ту же)
- [ ] Скриншоты 1280×800 сделаны с реального попапа
- [ ] Тексты Privacy из `docs/PRIVACY.md` перенесены в дашборд без противоречий
- [ ] Описание не перечисляет бренды списком и не повторяет ключевое слово >5 раз
